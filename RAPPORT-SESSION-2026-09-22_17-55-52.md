## 1. Décisions de migration (validées par l'utilisateur avant tout code)

- **Ordre** : frontend d'abord (Vite gère TS nativement, aucun impact sur le déploiement Render), backend ensuite — reporté à une prochaine session.
- **Runtime backend (à faire)** : compiler en JS (`tsc`) avant démarrage (`node backend/dist/server.js`) plutôt qu'exécuter le `.ts` directement via un loader — impactera `render.yaml`.
- **Niveau de rigueur visé** : `strict: true` à terme, une fois tous les fichiers convertis. En attendant, `allowJs: true` / `strict: false` pour cohabiter avec le JS restant.
- Méthode : un dossier par PR (`api/` → `stores/` → `composables/`+`components/`), CI verte + `npm run typecheck` + `npm run build` + `npm test` avant chaque merge, déploiement Render vérifié via `/api/health` après chaque merge.

| Symptôme | Cause | Correction |
|---|---|---|
| `computer screenshot` timeout CDP à plusieurs reprises pendant le test manuel | Flakiness de l'outil de capture d'écran dans cet environnement (probablement lié à la compilation à la volée de nombreux nouveaux modules `.ts`/`.vue` par esbuild au premier accès à chaque vue) — sans rapport avec le code de l'app : un `wait` de quelques secondes puis retry résolvait systématiquement, et l'état de la page (vérifié ensuite) était toujours correct | Pas de correction côté code — juste patienter et reprendre le screenshot |
| Onglet devenu complètement non réactif (clics et screenshots en timeout) en testant le bouton "Supprimer" de la modale | `window.confirm()` (natif, pré-existant dans `handleDelete`, comportement non modifié par la migration) bloque le thread JS de la page — CDP ne peut pas interagir avec une dialogue navigateur native | Onglet fermé (ce qui rejette la boîte de dialogue) ; nettoyage de l'événement de test effectué directement via l'API (`curl -X DELETE`) plutôt que par le bouton Supprimer de l'UI |

## 7. Prochaines étapes suggérées

1. Envisager la phase 5 (durcissement) : activer `strict: true` dans `frontend/tsconfig.json` maintenant que tout le frontend est converti, corriger les erreurs qu'elle révèle.
2. Démarrer la migration backend : `tsconfig.json`, choix du build (`tsc` → `dist/`), mise à jour de `render.yaml` (`buildCommand`/`startCommand`), conversion `routes/` → `controllers/` → `services/` → `utils/` → `server.js`, dans le même esprit une-PR-par-dossier.
3. Une fois backend et frontend en TS strict, ajouter un job `typecheck` à `.github/workflows/tests.yml` pour que la CI gate dessus.
4. Revérifier périodiquement si une version de `vue-tsc` compatible avec `typescript@7.x` est publiée, pour retirer l'épinglage à `6.0.3`.
