## 2. Issue #61 — bug de transition bloquée, puis vrai bug trouvé (double Échap)

PR [#63](https://github.com/arnaudbregere/agenda-app-event/pull/63), mergée en `45e2f13`, déployée et vérifiée (`/api/health` sur ce commit). Trois itérations sur la même PR.

| Itération | Contenu |
|---|---|
| 1 | `:duration` explicite sur les `<Transition>` (composable `useTransitionDuration.ts` lisant `--transition-base` à l'exécution) pour éviter une transition qui ne se termine jamais. |
| 2 (retour « fais simple ») | Composable retiré, remplacé par une constante `200` en dur. |
| 3 (retour : vrai bug rapporté) | Voir ci-dessous. |

**Le vrai bug**, rapporté par l'utilisateur : ouvrir la modale d'édition, ouvrir la confirmation de suppression, Échap (ferme la confirmation, OK), Échap une seconde fois (ne fermait plus la modale d'édition).

| Symptôme | Cause | Correction |
|---|---|---|
| Deuxième Échap sans effet après avoir fermé la confirmation de suppression | Un `<dialog>` ouvert répond nativement à Échap via son propre événement `cancel`, qui ferme la boîte côté DOM **avant** que le `@keydown` manuel ne la voie. `emit("cancel")` n'était donc jamais appelé par ce chemin ; `deleteConfirmOpen` restait bloqué à `true` côté Vue, et `EventModal` restait `inert` indéfiniment (`:inert="deleteConfirmOpen"`) | `ConfirmDialog` pilote désormais `<dialog>` nativement via `showModal()`/`close()` plutôt que de réimplémenter le comportement à la main : `:inert` retiré (le `<dialog>` modal rend nativement le reste du document inert), plus de piège de focus/restitution manuels (natifs via `showModal()`/`close()`), `autofocus` sur Annuler, `::backdrop` natif remplace le `<div>` overlay |

- `:duration` retiré aussi du `<Transition>` d'`EventModal.vue` (question de l'utilisateur : « est-ce nécessaire ? »). Réponse prouvée, pas supposée : lecture de `node_modules/@vue/runtime-dom` montre que le retrait de la classe `*-enter-from` se fait dans `nextFrame()` (double `requestAnimationFrame`), exécuté **avant** le code que `:duration` concerne — il ne protégeait donc même pas contre le point de blocage visé.
- jsdom n'implémente pas `HTMLDialogElement.showModal()/close()` (vérifié directement : `typeof el.showModal === "undefined"`) : polyfill minimal ajouté (`frontend/src/test-support/setup.ts`, chargé via `setupFiles` dans `vite.config.js`).
- Diff net de la simplification finale : **-58 lignes** (`git show 45e2f13 --stat` : 140 insertions, 161 suppressions).

**Investigation sur le blocage de transition original** : reproduit une seule fois de façon fiable dans l'outil `claude-in-chrome`, jamais confirmé comme un vrai bug pour un utilisateur réel. Un test isolé (double `requestAnimationFrame`, sans code de l'app) reste bloqué dans cet outil jusqu'à ce qu'une capture d'écran force un repaint, alors qu'un `setTimeout` fonctionne normalement — indice fort d'un artefact de l'outil d'automatisation plutôt qu'un bug applicatif. Signalé via `SendFeedback` (brouillon envoyé par l'utilisateur ensuite via `/feedback`, reçu confirmé `07be3a4f-2825-4e4c-94ea-06ac4e881a77`).
