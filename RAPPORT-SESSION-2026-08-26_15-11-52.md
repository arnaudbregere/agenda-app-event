## 1. Contexte initial

Clarifications obtenues avant de démarrer :

| Question | Réponse retenue |
|---|---|

| Fonctionnalités | CRUD simple + catégories/couleurs + recherche |

## 2. Backend (`backend/`)

Express + stockage fichier JSON (`backend/data/events.json`).

- **`server.js`** — point d'entrée, montage des routes, gestion d'erreurs centralisée, 404 JSON.
- **`src/routes/events.js`** — `GET/POST /api/events`, `GET/PUT/DELETE /api/events/:id`.
- **`src/routes/categories.js`** — `GET /api/categories`.
- **`src/controllers/eventsController.js`** — logique des handlers HTTP.
- **`src/services/eventsStore.js`** — accès au fichier JSON avec une **file de promesses** pour sérialiser les lectures/écritures (évite la corruption en cas de requêtes concurrentes) ; création automatique du fichier s'il n'existe pas.
- **`src/utils/validators.js`** — validation des payloads (titre requis, dates ISO valides, fin ≥ début, catégorie dans la liste autorisée, etc.).
- **`src/utils/categories.js`** — 6 catégories prédéfinies avec couleur (Personnel, Travail, Important, Famille, Loisirs, Autre), source de vérité pour la validation serveur.

Testé via `curl` : health check, création, listing, catégories — tout fonctionnel dès la première itération.

## 3. Frontend (`frontend/`)

Vue 3 + Vite + Pinia + `date-fns`, scaffoldé via `npm create vite@latest -- --template vue`.

### Architecture CSS — ITCSS

`frontend/src/styles/`, importé dans l'ordre par `main.css` :

1. **Settings** — tokens (`_colors.css`, `_spacing.css`, `_typography.css`, `_z-index.css`, `_breakpoints.css`), aucun sélecteur.
2. **Tools** — tokens composites réutilisables (ombres, transitions, focus ring).
3. **Generic** — reset CSS.
4. **Elements** — styles des balises HTML nues.
5. **Objects** — structures réutilisables sans style visuel (`o-app-shell`, `o-flex`, `o-scroll-y`…).
6. **Components** — UI concrète (`c-btn`, `c-app-header`, `c-month-grid`, `c-time-grid`, `c-event-pill`/`c-event-block`, `c-modal`, `c-form`, `c-mini-cal`, `c-category-filter`, `c-agenda-list`…).
7. **Utilities** — classes d'override (`u-visually-hidden`, `u-hidden`…).

### État applicatif (Pinia)

- **`stores/events.js`** — données (événements, catégories) + actions CRUD contre l'API.
- **`stores/calendar.js`** — état UI (vue courante, date courante, recherche, filtres de catégories, état de la modale), avec le getter `filteredEvents` qui croise recherche + filtres.

### Composables

- **`useCalendarGrid.js`** — génération des grilles (semaines du mois, jours de la semaine), détection "aujourd'hui", occurrence d'un événement sur un jour donné.
- **`useEventLayout.js`** — algorithme de layout des événements chronométrés qui se chevauchent (vues Semaine/Jour) : regroupement en clusters + attribution de colonnes gloutonne.

### Composants

`AppHeader`, `AppSidebar`, `MiniCalendar`, `CategoryFilter`, `EventModal` (création/édition avec validation, suppression), vues `MonthView`, `WeekView`/`DayView` (via `TimeGrid` partagé avec ligne "maintenant" en temps réel), `ListView` (agenda groupé par jour), plus des composants `ui/` (`BaseButton`, `Icon` avec un petit registre SVG inline, sans dépendance d'icônes externe).

### Vérification visuelle

Playwright installé (Chromium headless) pour un test end-to-end réel :
- Lancement backend + frontend en parallèle.
- Création d'un événement via l'UI, vérification de son affichage correct dans les 4 vues.
- Ouverture de la modale d'édition avec pré-remplissage correct.
- **Aucune erreur console** sur l'ensemble du parcours.
- Captures d'écran envoyées à l'utilisateur (vues Mois et Semaine).

Nettoyage post-test : `events.json` remis à `[]`, dépendances de test supprimées.

## 6. Préparation au déploiement

### Tentative Vercel → abandonnée

Vercel exécute le backend en fonctions serverless sans système de fichiers persistant : le stockage `events.json` (lecture/écriture disque direct) n'y serait pas fiable — les événements créés pourraient disparaître selon l'instance qui traite la requête suivante. Deux options ont été proposées à l'utilisateur (Vercel frontend + Render backend, ou tout Vercel avec changement de stockage vers une base de données) ; l'utilisateur a préféré **rester sur Render pour l'ensemble** de l'application.

### Montage retenu : service unique sur Render

- **`backend/server.js`** modifié pour servir `frontend/dist` en statique (avec fallback SPA) quand ce dossier existe, en plus de l'API `/api/*` — une seule URL en production, pas de souci CORS.
- **`frontend/src/api/client.js`** : URL de l'API par défaut passée de `http://localhost:4000/api` (en dur) à un chemin relatif `/api` en production ; `.env.development` continue de pointer vers `localhost:4000` en dev.
- **`render.yaml`** ajouté à la racine (blueprint Render : build du frontend puis install du backend, `startCommand: node backend/server.js`, health check sur `/api/health`).
- Testé en local : build du frontend + démarrage du backend seul → l'app complète (API + UI) répond correctement sur le port 4000.
- Commit `7732d16` poussé sur GitHub.
- Section **Déploiement** ajoutée au README, avec l'avertissement sur la non-persistance du disque en plan gratuit Render (le fichier `events.json` peut être réinitialisé entre redéploiements/redémarrages).

### Étape restante (côté utilisateur)

Je n'ai pas d'accès CLI/API à Render dans cet environnement (contrairement à `gh`). Il reste à :
1. Se connecter sur [dashboard.render.com](https://dashboard.render.com) (via GitHub).
2. **New +** → **Blueprint** → sélectionner `agenda-app-event` (Render détecte `render.yaml`).
3. **Apply** / **Deploy**.
4. Transmettre l'URL obtenue pour mise à jour du lien dans le `README.md`.
